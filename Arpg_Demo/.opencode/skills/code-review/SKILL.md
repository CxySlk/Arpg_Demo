## 阶段 1：加载目标文件

完整读取目标文件。读取 CLAUDE.md 获取项目编码标准。

---

## 阶段 2：识别引擎专家

读取 `.opencode/docs/technical-preferences.md` 中的 `## 引擎专家` 部分。注意：

- **主要**专家（用于架构和广泛的引擎问题）
- **语言/代码专家**（审查项目主要语言文件时使用）
- **着色器专家**（审查着色器文件时使用）
- **UI 专家**（审查 UI 代码时使用）

如果该部分显示 `[待配置]`，则未固定引擎 — 跳过引擎专家步骤。

---

## 阶段 3：ADR 合规性检查

在用户故事文件、提交消息和头注释中搜索 ADR 引用。查找 `ADR-NNN` 或 `docs/architecture/ADR-` 等模式。

如果未找到 ADR 引用，注明："未找到 ADR 引用 — 跳过 ADR 合规性检查。"

对于每个引用的 ADR：读取文件，提取**决策**和**后果**部分，然后分类任何偏差：

- **架构违规**（阻止性）：使用了 ADR 中明确拒绝的模式
- **ADR 漂移**（警告）：在未使用禁止模式的情况下，有意义地偏离了所选方法
- **轻微偏差**（信息）：与 ADR 指导的小差异，不影响整体架构

---

## 阶段 4：标准合规性

识别系统类别（引擎、游戏玩法、AI、网络、UI、工具）并评估：

- [ ] 公共方法和类有文档注释
- [ ] 每个方法的圈复杂度低于 10
- [ ] 没有方法超过 40 行（不包括数据声明）
- [ ] 依赖被注入（游戏状态没有静态单例）
- [ ] 配置值从数据文件加载
- [ ] 系统暴露接口（而非具体类依赖）

---

## 阶段 5：架构和 SOLID

**架构：**
- [ ] 正确的依赖方向（引擎 <- 游戏玩法，而非相反）
- [ ] 模块之间没有循环依赖
- [ ] 适当的层级分离（UI 不拥有游戏状态）
- [ ] 使用事件/信号进行跨系统通信
- [ ] 与代码库中已建立的模式一致

**SOLID：**
- [ ] 单一职责：每个类有一个变更原因
- [ ] 开闭原则：可扩展而无需修改
- [ ] 里氏替换：子类型可替代基类型
- [ ] 接口隔离：没有臃肿的接口
- [ ] 依赖倒置：依赖抽象而非具体

---

## 阶段 6：游戏特定问题

- [ ] 帧率独立性（delta time 使用）
- [ ] 热路径（update 循环）中没有分配
- [ ] 适当的空/空状态处理
- [ ] 需要时的线程安全
- [ ] 资源清理（无泄漏）

---

## 阶段 7：专家审查（并行）

通过 Task 同时生成所有适用的专家 — 不要等待一个完成再开始下一个。

### 引擎专家

如果已配置引擎，确定每个文件适用的哪个专家并并行生成：

- 主要语言文件（`.gd`、`.cs`、`.cpp`）→ 语言/代码专家
- 着色器文件（`.gdshader`、`.hlsl`、着色器图）→ 着色器专家
- UI 屏幕/控件代码 → UI 专家
- 跨领域或不明确 → 主要专家

对于任何涉及引擎架构（场景结构、节点层级、生命周期钩子）的文件，也生成**主要专家**。

### QA 可测试性审查

对于逻辑和集成用户故事，也通过 Task 并行生成 `qa-tester`。传递：
- 正在审查的实现文件
- 用户故事的 `## QA 测试用例` 部分（来自 qa-lead 的预写测试规范）
- 用户故事的 `## 验收标准`

要求 qa-tester 评估：
- [ ] 是否暴露了所有测试钩子和接口（未隐藏在私有/内部访问后）？
- [ ] 用户故事 `## QA 测试用例` 部分中的 QA 测试用例是否映射到可测试的代码路径？
- [ ] 是否有任何验收标准在实现时不可测试（例如硬编码值，无注入接缝）？
- [ ] 实现是否引入了现有 QA 测试用例未涵盖的新边缘情况？
- [ ] 是否有任何应有测试但没有的可观察副作用？

对于视觉/体验和 UI 用户故事：qa-tester 审查 `## QA 测试用例` 中的手动验证步骤在当前实现下是否可实现 — 例如"手动检查器需要达到的状态是否真的可达？"

在生成输出之前收集所有专家发现。

## 阶段 9：后续步骤

- 如果结论为已批准：运行 `/story-done [story-path]` 关闭用户故事。
- 如果结论为需要变更：修复问题并重新运行 `/code-review`。
- 如果发现架构违规：运行 `/architecture-decision` 记录正确方法。
